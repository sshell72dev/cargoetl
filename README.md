# CargoETL — dispatcher board

Рейтинг диспетчеров для TMS по грузоперевозкам США. Бонусы считаются с этого экрана, поэтому каждое спорное правило записано явно: в API, в тестах и в блоке «What did not count».

Локальная демка: [http://127.0.0.1:3000](http://127.0.0.1:3000).  
Репозиторий: [https://github.com/sshell72dev/cargoetl](https://github.com/sshell72dev/cargoetl).  
Vercel: API `cargoetl-api`, UI `cargoetl-board` (URLs после первого деплоя).

## Как запустить

Данные уже лежат в `data/` (seed 42). Две команды из корня:

```bash
python -m pip install -r backend/requirements.txt && npm --prefix frontend install
python start.py
```

Откроется UI на [http://127.0.0.1:3000](http://127.0.0.1:3000), API на [http://127.0.0.1:8000/api/leaderboard?period=2026-07](http://127.0.0.1:8000/api/leaderboard?period=2026-07).

Перегенерировать датасет: `python scripts/generate_data.py`  
Тесты: `python -m pytest backend/tests -q` (запускать из `backend/` или с `pythonpath`).

Часы в данных — UTC. Период по умолчанию — **июль 2026** (последний полный месяц относительно демо-сейчас `2026-08-14`).

## Краевые случаи: что нашёл и как решил

Это главный пункт. Рейтинг двигает деньги, поэтому я не «усреднял спорное», а выбирал правило, которое можно объяснить диспетчеру за 20 секунд.

### 1. Кто получил маржу, если бронировал один, а закрыл другой

**Засчитал `closedBy`.** Бронирование — навык найти груз и ставку; закрытие — момент, когда компания реально получает деньги. Задание говорит: в зачёт идут доставленные. Значит бонусный пул — у того, кто довёл.

Брокеру это обидно, если он отдал смену. Поэтому на карточке отдельно видны booked $ / handed off / taken. Handoff не теряется как факт, но не режет маржу пополам: 50/50 на бонусах порождает вечные споры «кто больше сделал».

Посаженный груз: `L-HANDOFF-01` (Priya забронировала, Marcus закрыл) — июль идёт Marcus.

### 2. Граница месяца: забронирован в июле, доставлен в августе

**Месяц = месяц `deliveredAt`.** P&L кассира, не CRM. `L-CROSS-MONTH` в июле в блоке excluded как `deferred_to_delivery_month`, в августе — в рейтинге Aisha Bennett.

Иначе команда бронирует пачку 31-го числа и красит месяц, который ещё не заработал.

### 3. UTC vs таймзоны диспетчеров

Границу суток **не** считаю в таймзоне человека. Иначе один и тот же delivery в `2026-08-01T04:30:00Z` — это 31 июля 23:30 в Чикаго и 1 августа 00:30 в Нью-Йорке. Восточный диспетчер утащил бы груз в другой бонусный месяц.

**Компанейские часы: `America/Chicago`.** US trucking почти всегда живёт Central. Таймзона диспетчера показывается на карточке и не участвует в `period_bounds`.

Посаженный груз: `L-TZ-BOMB` — Priya (America/New_York), доставка 04:30Z 1 августа. В рейтинге это **июль**. Тест `test_timezone_boundary_uses_company_clock_not_dispatcher_clock`.

### 4. Отмены

Не в рейтинге. Маржа на бумаге в excluded, reason `cancelled`. Отмена — это не «почти заработали». `L-CANCEL-01`.

### 5. Отрицательная и нулевая маржа

**Входит в сумму.** Спрятать убыток = нарисовать бонус. На строке бейдж `loss`. `L-NEG-01`, `L-ZERO-MARGIN`.

### 6. Нет closer у доставленного груза

Не приписываю booker молча. Это дыра в данных, а не «очевидно его». `L-NO-CLOSER` → `missing_closer`, деньги компании в company totals тоже не размазываются по людям. На дашборде это видно как незакрытый хвост.

### 7. Новичок вышел 16 июля

Jade Ortega (`D-24`) в июле 16 активных дней. **Официальное место — по сумме маржи**, как у всех. Иначе два жирных груза за три дня выигрывают месяц.

Рядом метрика **$ / active day** и отдельный тумблер Fairness на лидерборде. Тумблер честно подписан: это не бонусный сорт. Partial-period бейдж `16/31 days`.

Уволенный `D-25` (20 июня) в июле не ранжируется (0 дней, 0 closes). Его июньские закрытия остаются в июне — бонус уже заработан.

Нора Ким (`D-26`) вышла 3 августа, в июле пустая — не занимает место «нуля».

### 8. Ничья

`D-09` Nina Petrov и `D-10` Omar Haddad в июле имеют **одинаковую** closed margin до цента (`L-TIE-ADJUST` в генераторе). Место общее, следующее пропускается: 1, 2, 2, 4. Не «кто раньше в алфавите». Алфавит только для стабильной отрисовки строк с одним rank.

### 9. Что считается «не попало в расчёт»

API отдаёт не только таблицу, но и `excluded.summary` + семплы с причиной. На экране это блок **What did not count**. Диспетчер должен иметь возможность ткнуть в число, а не спорить с Excel.

## Какие метрики и почему

Обязательные: **место + динамика к прошлому месяцу**, **closed $**, **число закрытых грузов**.

Добавил:

| Метрика | Зачем |
|---|---|
| **$ / active day** | Сравнить новичка со старожилом, не ломая официальный рейтинг |
| **RPM (margin / miles)** | Объём легко накрутить короткими дешёвыми грузами. RPM показывает качество ставки |
| **Avg margin / load** | Охотится ли человек за жирными lane или за штуками |
| **Booked $ vs closed $**, handoffs | Не потерять брокера в модели «кредитуем closer» |
| **Loss loads** | Убытки видимы, не усреднены |

Не стал делать on-time: в схеме нет appointment window, выдумывать SLA стыдно.

## Что не делал

- Авторизация, роли, CI, дизайн-система — по заданию не нужны.
- Сплит маржи 50/50 на handoff — сознательно нет, см. выше.
- Нормализация рейтинга по дням как **официальный** сорт — нет, это ломается двумя грузами.
- Настоящий realtime ingest. Live — **replay ленты 13–14 августа по SSE**, подписано на экране. Датасет статический, выдумывать новые грузы каждые 3 секунды было бы враньём.
- Денормализация в SQL. JSON + расчёт в памяти: 1.2k грузов, пересчёт мгновенный, правила читаются.
- Идеальная мобильная вёрстка. Это десктоп диспетчерской.

Экраны: все четыре. Leaderboard — основной.

## Где модель ошиблась

Первый черновик движка потащил `python-dateutil` ради `relativedelta` — лишняя зависимость на сдвиг месяца. Поймал, пока смотрел `requirements.txt`, заменил на десять строк `_shift_month`.

Вторая ошибка опаснее: модель начала считать границу месяца **в таймзоне диспетчера**. На `L-TZ-BOMB` это разъехалось бы с Chicago. Поймал, когда явно выписал UTC 04:30 1 августа в CDT и EDT. Правило компании оставил одним, тест написал до того, как трогать UI.

Третье: проксировать SSE через Next rewrite. Next буферизует стрим, Live «оживает» пачкой. EventSource ходит на API напрямую, JSON по-прежнему через rewrite — без CORS-плясок на лидерборде.
